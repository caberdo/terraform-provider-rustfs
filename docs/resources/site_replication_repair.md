# rustfs_site_replication_repair Resource

Repair a RustFS site-replication group.

Creating this resource reconciles every peer's site-replication state: the provider asks RustFS for a dry-run plan, executes it, and stores the resulting operation. The route is synchronous, so `status` is terminal when the apply finishes (`success` or `partial`). A `partial` result reports which site and family still have failures in `sites`; re-create the resource (for example with `terraform taint`) to retry.

**Repair mutates data.** It rewrites bucket targets and IAM items on the peers, so `confirm` must repeat the provider `endpoint`. RustFS persists a bounded history of operations and prunes the oldest successful ones; when the record for this resource has been pruned, `Read` keeps the last observed state instead of forgetting the repair and running it again.

Destroying this resource does nothing on the server: a repair cannot be undone. It only forgets the operation record.

Import sets `operation_id` from the import ID; the configuration must still carry `confirm` before the next plan.

## Example Usage

```terraform
resource "rustfs_site_replication" "peer" {
  name       = "peer"
  endpoint   = "http://peer.example.com:9001"
  access_key = "rustfsadmin"
  secret_key = var.peer_secret
}

resource "rustfs_site_replication_repair" "repair" {
  # Must match the provider "rustfs" endpoint: it names the cluster being repaired.
  confirm = var.rustfs_endpoint

  depends_on = [rustfs_site_replication.peer]
}
```

## Schema

### Required

- `confirm` (String) Safety interlock: must repeat the provider `endpoint` without its scheme (for example `127.0.0.1:9001`, even when `endpoint` is `https://127.0.0.1:9001`). A repair reconciles every peer and can rewrite bucket targets and IAM items, so naming the cluster makes the operation deliberate and stops a configuration copied to another environment from repairing the wrong deployment.

### Optional

- `operation_id` (String) Repair operation ID. Leave unset to let the provider generate a UUID, or set it to choose the ID of the new repair. Changing it starts a new repair; import an existing operation with `terraform import`. Set it explicitly when a failed apply may have reached the server: the operation can keep running, and a later import by that ID adopts it. If the server records the operation under a different ID, `id` reports that canonical value while this attribute keeps the configured one.

### Read-Only

- `completed_at` (String) Time the operation completed, in RFC 3339. Null while it is still running.
- `created_at` (String) Time the operation was created, in RFC 3339, as reported by the server.
- `id` (String) Canonical repair operation ID the server records. It matches `operation_id` unless RustFS normalised the requested value.
- `retry_events` (Number) Number of retry-queue events the dry-run plan replays during the repair.
- `sites` (Attributes List) Per-site repair progress, one row per site and repair family, ordered by deployment ID and family name. A site that reports no repair families appears once with an empty `family`. (see [below for nested schema](#nestedatt--sites))
- `status` (String) Repair status reported by the server: `success`, `partial` or `running`. RustFS reports `partial` when at least one task failed; the per-site detail is in `sites`.
- `updated_at` (String) Time the operation was last updated, in RFC 3339, as reported by the server.

### Nested Schema for `sites`

Read-Only:

- `deployment_id` (String) Deployment ID of the site.
- `errors` (List of String) Errors reported for this site and family.
- `failed` (Number) Tasks that failed.
- `family` (String) Repair family (RustFS currently reports `replication`).
- `name` (String) Configured name of the site.
- `planned` (Number) Tasks planned for this site and family.
- `retry_events` (Number) Retry-queue events replayed for this site and family.
- `succeeded` (Number) Tasks that succeeded.
